# 《花月》玩家遊戲日曆（Player Calendar）企劃書

> **資料類模組，非遊戲類**
> 掛載於「青雲梯」（[learningPath.js](../learningPath.js)）頂部列，`.lp-header` 旁新增一顆日曆按鈕開啟彈窗。
> 介面風格沿用 [achievement.css](../achievement.css) 的紅底分頁卡片系（`.ach-overlay`/`.ach-container` 家族），與「成就與紀錄」「排行榜」並列為玩家自我成長的第三面鏡子。
> 區別：「成就與紀錄」看的是**累積了什麼**；「排行榜」看的是**自己 vs. 所有人**；「遊戲日曆」看的是**這個月，我每一天投入了多少**。
>
> 資料層依據：[排行榜彙總表_SQL草案.sql](排行榜彙總表_SQL草案.sql) 第 1.2 節 `player_daily_stats`、第 5.7～5.8 節 `get_player_calendar` / `get_player_month_summary`。

---

## 1. 模組目標

### 1.1 為什麼需要遊戲日曆？

排行榜回答「我贏過誰」，成就系統回答「我解鎖了什麼」，但兩者都無法回答一個更貼身的問題：

> **「我這個月，有沒有每天都在讀詩？」**

花月的核心學習理論是提取練習（retrieval practice），而提取練習的效果高度依賴**規律性**——三天打魚兩天曬網的效果遠不如每天一小段。遊戲日曆把「規律」這件抽象的事情變成一張看得見的月曆：滿格的綠色連成一片，斷掉的白格子刺眼地留在那裡。這是比任何排行榜名次都更誠實的鏡子，因為它不跟別人比，只跟「昨天的自己」比。

### 1.2 設計原則

| 原則 | 說明 |
|---|---|
| **兩種局都算數，但分開記** | 青雲梯的晉升局與漢堡選單的自由練習都是「有在讀詩」，都該讓格子亮起來；但彈窗細節要讓玩家看清楚「今天有沒有推進晉升進度」，避免只顧著刷自由練習卻沒有實質升階。 |
| **色階獎勵持續，不獎勵爆肝** | 五段色階（綠／藍／紅／紫／金黃）門檻採**對數級距**（15/30/60/120），意味著「從 0 局到 15 局」與「從 60 局到 120 局」帶來同樣一階的視覺升級，避免玩家誤以為必須無限堆量才看得到進步。 |
| **月度色條是意志力的溫度計** | `board-top` 色條把整個月的累積局數變成彈窗上緣的一眼即知的視覺語言，玩家不用心算就知道這個月的狀態。 |
| **文錢分兩條線，各自講一個故事** | 「玩遊戲賺的文錢」與「晉升文位／領獎狀／江南小院賺的文錢」分開顯示，是為了讓玩家看見：只靠青雲梯刷分不是唯一的路，多練習、多考試、多經營小院也能致富——這是引導玩家探索花月其他模組的鉤子。 |
| **只讀不寫** | 日曆本身不產生任何新的遊戲行為，純粹是既有 `game_logs` 與文錢事件的可視化彙整，不影響任何既有數值。 |

## 2. 遊戲玩法與核心操作

嚴格來說這不是「遊戲」，但比照規範仍以此框架描述互動流程。

### A. 使用流程（一次開啟的完整時間序）

1. 玩家在青雲梯主畫面點擊頂部列新增的日曆圖示按鈕（`.lp-calendar-btn`）。
2. 彈出遮罩層 `.pc-overlay`，主卡 `.pc-container` 以淡入方式浮現，預設顯示**當月**。
3. 系統呼叫 `get_player_calendar(playerId, monthStart, monthEnd)` 與 `get_player_month_summary(playerId, monthStart, monthEnd)`，撈回本月每日彙總與月度合計。
4. 月曆格子依當日 `ranked_wins + practice_wins` 局數套上對應底色（見 §4.2 色階表），無資料的日子維持米白底。
5. 彈窗上緣 `board-top` 色條依月度合計局數套色（見 §4.3）。
6. 下緣統計列顯示本月累積：晉升局數／練習局數／文錢（分兩行，見 §3.C）。
7. 玩家左右滑動（或點擊左右箭頭）切換月份 → 觸發步驟 3 重新查詢該月資料。
8. 玩家點擊某一天的格子 → 彈出當日明細小卡（見 §3.D）。
9. 點擊關閉或遮罩區 → 彈窗淡出，回到青雲梯主畫面。

### B. 操作方式

**桌機**：滑鼠點擊左右箭頭切月；點擊格子開明細卡；`Esc` 關閉整個彈窗。
**手機**：月曆區支援**水平滑動手勢**切月（`touchstart`/`touchmove`/`touchend` 偵測位移量，仿照 `screen_adaptive.js` 既有的觸控慣例），同時保留箭頭按鈕作為備援，避免手勢誤判；點擊格子開明細卡；點擊遮罩區關閉。

**手機觸控矛盾與解法**：
- **手勢衝突**：月曆容器內的水平滑動與瀏覽器/彈窗的垂直捲動手勢方向不同，理論上互不干擾；但若玩家斜向滑動，需設定角度閾值（水平位移 > 垂直位移 × 1.5 才判定為切月手勢），否則會誤觸發切月。
- **格子過小導致誤觸**：手機寬度下月曆需保持 7 欄，單格寬度可能小於 44px 的建議最小觸控尺寸。解法：格子本體只負責視覺與底色，實際可點擊區域用 `padding` 撐大到最小 44×44px，不縮小格子間的視覺留白。

### C. 即時反饋機制

- 切月時，月曆區域有一個短暫（150ms）的橫向滑出/滑入過場，強化「翻頁」感，同時作為資料載入中的緩衝視覺。
- 點擊格子時該格短暫放大（`transform: scale(1.08)`）再彈出明細卡，給予「這格被選中了」的明確回饋。
- 有紀錄的格子 hover（桌機）／按下（手機）時邊框輕微發光，提示「這格可以點」。

### D. 無資料狀態

- 當月完全無紀錄（新玩家、或還沒登入雲端）：月曆維持全米白，下緣統計列顯示「這個月還沒有記錄，去青雲梯打一局試試？」，`board-top` 維持預設淺咖啡色。
- 未來月份（尚未發生）：格子顯示為更淺的灰白，不可點擊，滑動仍可切換但不查詢（前端直接跳過 RPC 呼叫）。

### B. 視覺回饋系統（格子底色，對應 §4.2 色階）

| 狀態 | 底色 | 說明 |
|---|---|---|
| 無紀錄 | 米白 `var(--fm-paper-card)` | 預設態 |
| 1～15 局 | 綠 `var(--fm-celadon)` 淡化版 | 入門的一天 |
| 16～30 局 | 藍 | 穩定的一天 |
| 31～60 局 | 紅 | 投入的一天 |
| 61～120 局 | 紫 | 全力衝刺的一天 |
| 121 局以上 | 金黃 `var(--fm-gold)` | 爆肝紀念 |

配色沿用花月既有的 `--fm-*` 變數家族，不另創新色票；紫色需新增一個 `--fm-violet` 變數（目前主題色板中沒有紫色，需與美術確認一個與朱紅/翠綠/金黃色階同飽和度的紫，避免突兀）。

### C. board-top 色條（月度合計局數）

| 月度總局數（`ranked_wins + practice_wins`） | 色條顏色 |
|---|---|
| 0 | 淺咖啡色（預設） |
| ≥ 1（15×1） | 綠 |
| ≥ 225（15×15） | 藍 |
| ≥ 450（30×15） | 紅 |
| ≥ 900（60×15） | 紫 |
| ≥ 1800（120×15） | 金黃 |

門檻邏輯 = 「格子色階的每日下限 × 15 天」，也就是「這個月平均每天都達到某個格子色階」的近似值。這個設計讓 `board-top` 的顏色與格子色階系統共享同一套視覺語言，玩家不需要學兩套規則。

### D. 計時器/動態元素

日曆模組沒有計時器，唯一的動態元素是切月時的滑動過場（見 §2.C）。

### E. 使用體驗的流暢度設計

- 月曆資料以「月」為單位快取（比照 `leaderboard.js` 既有的 60 秒快取慣例），同一月份 60 秒內重複開啟不重新查詢。
- 快速連續點擊左右箭頭時，只送出最後一次的查詢請求（debounce 200ms），避免切月過快時舊資料蓋掉新資料。

## 4. 遊戲機制的繼承與創新

**繼承**：介面骨架完全繼承自「排行榜」與「成就與紀錄」共用的 `.ach-*` 紅底卡片系統，玩家不需要學習新的視覺語言。月曆本體的網格佈局繼承通用月曆 UI 慣例（週一起始、7 欄）。

**創新**：
1. **雙軌局數統計**：市面上少見的「日曆熱力圖」（如 GitHub 貢獻圖）通常只統計單一種活動量，花月版本刻意把「晉升局」與「練習局」分開計數但合併顯色，讓玩家在一眼看到投入量的同時，還能點進去看清楚自己是在扎實升階還是在悠閒複習。
2. **色條與格子共用同一套門檻邏輯**：`board-top` 的五段門檻直接由格子門檻乘以 15 推導而來，而不是另訂一套百分位或平均值算法，讓玩家不需要理解兩套規則，「月度色條」直觀地等於「這個月每天平均落在哪個格子顏色」。
3. **文錢雙源可視化**：把「玩遊戲賺的文錢」與「晉升文位／領獎狀／江南小院賺的文錢」並列呈現，是一個刻意的行為引導設計——目的是讓過度依賴青雲梯刷分的玩家看見「原來我這個月在江南小院也賺了不少」，進而被引導去探索考試與經營玩法。

## 5. 資料層設計

### 5.1 為什麼不需要新的明細表

日曆需要的資料形狀（一位玩家、一天、幾個數字）與排行榜重構後的 `player_daily_stats`（見 [排行榜彙總表_SQL草案.sql](排行榜彙總表_SQL草案.sql) 第 1.2 節）完全一致，等於免費搭上排行榜重構的便車：

```
player_daily_stats (player_id, day)  ← 主鍵，一位玩家一天一列
    games, wins, score_sum, duration_sum   ← 排行榜既有欄位
  + ranked_wins    -- 晉升局數（青雲梯／關卡模式）
  + practice_wins  -- 練習局數（漢堡選單自由練習）
  + silver_game    -- 當日玩遊戲賺的文錢
  + silver_bonus   -- 當日晉升文位／領獎狀／江南小院賺的文錢
  + silver_spent   -- 當日花掉的文錢
```

日曆一次只查一個月（最多 31 列），不受保留期政策影響——即使 90 天前的 `game_logs` 明細被清除，`player_daily_stats` 的彙總數字依然完整保留，玩家可以無限期往回滑動月曆查看歷史。

### 5.2 兩張表撐起「兩種局」與「兩種文錢」

- **兩種局**（晉升 vs 練習）：靠 `game_logs` 新增的 `is_ranked` 欄位分流，由 `LevelTable.getContext()` 是否非空判定，寫在 `supabaseClient.logGame` 內部，前端 41 個呼叫點不變。
- **兩種文錢**：
  - `silver_game`：由 trigger 直接從 `game_logs.score` 推算（`floor(score/100)`），**不需要**前端額外上傳。
  - `silver_bonus` / `silver_spent`：來自新表 `silver_events`（流水帳），需要前端在文錢異動時額外寫一筆。詳見 SQL 草案第 1.5 節與第 7.4 節；`source` 欄位規劃如下（依實際程式碼逐處核對後定案）：

| source | 對應 collection.js 位置 | 說明 |
|---|---|---|
| `cert` | achievement.js:2202 | 領取獎狀 |
| `rank` | ⚠️ 尚未實作，見下方說明 | 晉升文位本身的文錢獎勵 |
| `harvest` | collection.js:1333 | 採收田地 |
| `tea` | collection.js:1421 | 收取烘茶 |
| `wine` | collection.js:1462 | 開甕入庫 |
| `scribe` | collection.js:1518 | 抄本取回 |
| `sell` | collection.js:1742 | 江南小院倉庫賣出物品 |
| `exam_fee` | collection.js:1867 | 考試報名費（支出） |
| `decorate` | collection.js:1757 | 購買布置物件（支出） |

> **⚠️ `rank`（晉升文位文錢獎勵）確認為設計中的既定功能，目前尚未實作。**
> 這件事對本模組有實質影響：日曆的 `silver_bonus`／`board-top` 色條、以及排行榜彙總層的
> `player_daily_stats.silver_bonus`，都預期未來會多一路資料源。實作順序建議：
> 1. 晉升文位獎勵邏輯本身（`learningPath.js` 的 `showPromotionPopup` 或其對應的晉升判定處，
>    比照 `achievement.js:2174` 起的 `silverReward` 發放模式，補上發放與 UI 提示）落地時，
>    **務必同步呼叫 `FMCollectionSave.addSilver(collData, amount, 'rank', station.name)`
>    並在其後照常 `save(collData)`**，
>    不要延用舊模式直接 `data.silver += x`，否則又會製造一個新的未收口寫入點。
> 2. `get_player_calendar` / `get_player_month_summary` 兩支 RPC 完全不需要改——
>    `silver_bonus` 已經是對 `silver_events` 做 `sum(amount)`，新的 `source='rank'`
>    事件插入後會自動被既有邏輯納入加總，這是 §5.4 收口設計的價值所在。
> 3. 日曆 UI 本身也不需要改——明細小卡與下緣統計列顯示的是 `silver_bonus` 的加總值，
>    不區分 source，`rank` 上線當天玩家會直接看到「其他文錢」數字變多，不需要額外開發。

### 5.3 查詢 RPC

- `get_player_calendar(p_player_id, p_from, p_to)` → 回傳該區間每一天的 `ranked_wins / practice_wins / total_wins / score_sum / silver_game / silver_bonus / silver_spent`，供月曆格子與明細小卡使用。
- `get_player_month_summary(p_player_id, p_from, p_to)` → 回傳整個區間的加總，供下緣統計列與 `board-top` 色條門檻判定使用。

兩者皆已在 SQL 草案第 5.7～5.8 節備妥，`grant execute` 給 `anon`。

### 5.4 待補的技術債（與日曆同時處理，避免文錢記錄繼續散落各處）

`collection.js` 目前有 7 處各自 `data.silver += x; save(data)`，加上 `achievement.js` 與 `scoreManager.js` 各一處，共 9 個文錢異動點分散在 3 個檔案。建議在 `fmCollectionSave.js` 新增：

```js
// 實際採用的簽章（與初版草案不同，原因見下方說明）
addSilver: function (data, amount, source, note) {
    if (!data) return 0;
    amount = Math.round(Number(amount) || 0);
    if (amount === 0) return data.silver || 0;
    data.silver = (data.silver || 0) + amount;
    try {
        if (window.SupabaseClient && typeof window.SupabaseClient.logSilverEvent === 'function') {
            window.SupabaseClient.logSilverEvent({ amount, source, note });
        }
    } catch (e) { console.warn('[FMCollectionSave] 文錢流水帳寫入失敗:', e); }
    return data.silver;
}
```

> **⚠️ 為什麼簽章要收 `data` 且不自行存檔（初版草案的寫法會弄丟文錢）**
>
> 初版草案設想的是 `addSilver(amount, source, note)`，內部自行 `load()` → 改 → `save()`。
> 這個寫法套到 `collection.js` 會**直接造成文錢遺失**，因為該模組全程操作
> 記憶體中的 `this.data`，並在一整批異動完成後才存檔一次。以採收為例：
>
> ```js
> this.data.silver += price;          // ← 若改成自行 load/save 的 addSilver
> this.addInv(p.kind, tier);          //   這裡的 this.data.silver 並未被加值
> this.data.plots[idx] = emptyPlot();
> window.FMCollectionSave.save(this.data);  // ← 這一存，剛才加的錢就被蓋掉了
> ```
>
> 因此正確的設計是：`addSilver` 只就地修改呼叫端持有的 `data` 物件並記錄流水帳，
> **存檔仍由呼叫端原本的 `save(data)` 負責**，呼叫端的存檔時機一行都不必動。

`collection.js` 的 7 處與 `achievement.js` 的 1 處改呼叫 `FMCollectionSave.addSilver(...)`，`scoreManager.js` 那處（遊戲得分文錢）維持原樣不動——它由 trigger 從 `game_logs` 自動推算，刻意不重複寫入 `silver_events`。這件事的價值不只是日曆，而是往後任何新增的文錢來源都會自動被日曆與未來的「文錢流水帳」功能記錄到，不會再漏。
