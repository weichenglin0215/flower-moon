## 1. leaderboard.js

### 1.1 fetchShortBoard（日／週／月總分榜）

**現況問題**：`select('player_id,score')` 沒有分頁也沒有 limit，PostgREST 預設只回 1000 列，
所以現在的日／週／月榜在資料量超過 1000 局之後就已經是錯的。

```js
/** 短期榜：日/週/月區間總分，改由資料庫端加總排序 */
fetchShortBoard: async function (slice) {
    const sb = this.getSupabase();
    if (!sb) return this.fallbackSinglePlayer();

    const cacheKey = 'short_' + slice;
    if (this.cache[cacheKey] && (Date.now() - this.cache[cacheKey].ts < 60_000)) {
        return this.cache[cacheKey].data;
    }

    // p_slice: 'day' | 'week' | 'month' | 'all'
    // 分日基準為 Asia/Taipei，與資料庫端一致；前端不再自行算區間起點
    const { data, error } = await sb.rpc('get_short_board', {
        p_slice: slice || 'day',
        p_limit: 50
    });
    if (error) throw error;

    const rows = (data || []).map(r => ({
        id:          r.player_id,
        nickname:    r.nickname,
        global_rank: r.global_rank,
        total_score: Number(r.total_score) || 0
    }));

    this.cache[cacheKey] = { ts: Date.now(), data: rows };
    return rows;
}
```

順帶可刪除的東西：
- `sliceSince()` 整個函式（區間計算已移到 SQL 端）。
- 原本 `nickname: (pid.split('#')[0] || pid)` 的湊合寫法 —— RPC 已 join `player_saves`，
  回傳的是玩家自訂暱稱與真實 `global_rank`，不再需要從引繼碼硬切字串。

### 1.2 fetchGameBoard（單遊戲榜）

**現況問題**：撈 200 筆再用 JS 去重取每人最佳，200 筆之外的玩家紀錄直接看不到；
`clearCount` 走的是另一條路（`player_saves.games[].playCount`），三種 sub 兩套資料源。
改版後三種全部走 `player_game_stats`，資料源統一。

```js
/** 單遊戲榜：高分 / 速通 / 累計通關，三者共用同一支 RPC */
fetchGameBoard: async function (sub, gameKey, difficulty) {
    const sb = this.getSupabase();
    if (!sb) return this.fallbackSinglePlayer();

    const gameNo = parseInt(gameKey.replace('game', ''), 10) || 0;
    const cacheKey = 'gb_' + sub + '_' + gameKey + '_' + difficulty;
    if (this.cache[cacheKey] && (Date.now() - this.cache[cacheKey].ts < 60_000)) {
        return this.cache[cacheKey].data;
    }

    // sub 的三種值與 RPC 的 p_mode 同名：highScore / speedrun / clearCount
    const { data, error } = await sb.rpc('get_game_board', {
        p_game_no:    gameNo,
        p_difficulty: difficulty,
        p_mode:       sub,
        p_limit:      50
    });
    if (error) throw error;

    const rows = (data || []).map(r => ({
        id:          r.player_id,
        nickname:    r.nickname,
        global_rank: r.global_rank,
        total_score: Number(r.value) || 0,
        _isTime:     (sub === 'speedrun'),   // 渲染端據此把數字格式成 mm:ss
        _bestScore:  r.best_score,           // 速通榜可順便顯示該成績的分數
        _winCount:   r.win_count
    }));

    this.cache[cacheKey] = { ts: Date.now(), data: rows };
    return rows;
}
```

**行為差異（需知會玩家或寫進更新說明）**：
- 速通榜排除 `duration_s = 0` 的局。舊版沒排除，0 秒紀錄會霸榜。
- 累計通關榜從「`player_saves` 的 playCount（含所有難度）」改成
  「該遊戲**該難度**的 win_count」。舊版的 playCount 不分難度，
  跟榜單標題寫的「某難度」其實對不上，這次一併修正。

```js
fetchTimeBoard: async function (sub) {
    const sb = this.getSupabase();
    if (!sb) return this.fallbackSinglePlayer();

    if (sub !== 'totalTime') return this.fallbackSinglePlayer(); // streak 仍未實作

        total_score: Number(r.duration_sum) || 0,
        _isTime:     true
    }));

    this.cache[cacheKey] = { ts: Date.now(), data: rows };
    return rows;
}
```

### 2.1 loadStats：整段 while 迴圈刪掉

```js
async function loadStats() {
    const supabase = window.SupabaseClient.getClient();
    if (!supabase) { alert('Supabase 未連線'); return; }

    const dateFrom = document.getElementById('statsFrom').value;
    const dateTo   = document.getElementById('statsTo').value;
    document.getElementById('statsStatus').textContent = '載入中...';

    try {
        // 三支 RPC 平行發出，資料庫端已彙總，回傳量以「日數 / 遊戲數 / 30 名玩家」計，
        // 不再隨局數成長，也不再受 PostgREST 1000 列上限影響
        const [daily, gameDiff, playerRank] = await Promise.all([
            supabase.rpc('get_daily_overview',    { p_from: dateFrom, p_to: dateTo }),
            supabase.rpc('get_game_diff_stats',   { p_from: dateFrom, p_to: dateTo }),
            supabase.rpc('get_player_rank_stats', { p_from: dateFrom, p_to: dateTo, p_limit: 30 })
        ]);
        if (daily.error)      throw daily.error;
        if (gameDiff.error)   throw gameDiff.error;
        if (playerRank.error) throw playerRank.error;

        const totalGames = (daily.data || []).reduce((s, d) => s + Number(d.games), 0);
        document.getElementById('statsStatus').textContent =
            '區間共 ' + totalGames + ' 局（已彙總）';

        renderStats(daily.data || [], gameDiff.data || [], playerRank.data || []);
    } catch (e) {
        document.getElementById('statsStatus').textContent = '載入失敗: ' + e.message;
    }
}
```

同時可以拿掉的東西：
- `statsLimit` 這個輸入欄（「讀取上限 100～5000」）。它存在的唯一理由是舊架構要撈明細，
  現在沒有明細可撈了。**留著反而會誤導人以為統計有截斷。**
- `BATCH` / `from` / `allLogs` 等變數。

### 2.2 renderStats：改成吃三包彙總資料

```js
function renderStats(daily, gameDiff, playerRank) {
    /* ---- 頂部四張數字卡 ---- */
    // daily 已是「一天一列」，today / 近 7 天直接從陣列尾端取
    const todayStr = new Date().toLocaleDateString('sv-SE', { timeZone: 'Asia/Taipei' }); // YYYY-MM-DD
    const todayRow = daily.find(d => d.day === todayStr);
    const last7    = daily.slice(-7);

    document.getElementById('statTodayPlayers').textContent = todayRow ? todayRow.players : 0;
    document.getElementById('statTodayGames').textContent   = todayRow ? todayRow.games   : 0;
    document.getElementById('statWeekGames').textContent    =
        last7.reduce((s, d) => s + Number(d.games), 0);

    // ⚠️ 「近 7 天不重複人數」是唯一無法從日彙總正確還原的數字
    //    （同一人跨兩天會被算兩次）。處理方式見下方「已知取捨」。
    document.getElementById('statWeekPlayers').textContent =
        last7.reduce((s, d) => Math.max(s, Number(d.players)), 0); // 改為「單日最高在線人數」

    /* ---- 每日上線人數 / 每日局數 ---- */
    const days = daily.map(d => d.day);
    renderChart('chartDailyPlayers', 'bar', days, daily.map(d => Number(d.players)), '上線人數', '#4e79a7');
    renderStackedVBar('chartDailyGames', days,
        daily.map(d => Number(d.wins)),
        daily.map(d => Number(d.fails)), '#e15759');

    /* ---- 每遊戲 / 每難度 / 遊戲×難度 ---- */
    // gameDiff 是 (game_no, difficulty) 的細格，前端只需 group 兩次，不再逐筆 forEach
    const byGame = {}, byDiff = {}, byGameDiff = {};
    gameDiff.forEach(r => {
        const name = GAME_NAMES[r.game_no] || 'Game' + r.game_no;
        const w = Number(r.wins), f = Number(r.fails);

        if (!byGame[name]) byGame[name] = { win: 0, fail: 0 };
        byGame[name].win += w; byGame[name].fail += f;

        const d = r.difficulty || '(未填)';
        if (!byDiff[d]) byDiff[d] = { win: 0, fail: 0 };
        byDiff[d].win += w; byDiff[d].fail += f;

        if (!byGameDiff[name]) byGameDiff[name] = { fail: 0 };
        byGameDiff[name][d] = (byGameDiff[name][d] || 0) + w;
        byGameDiff[name].fail += f;
    });
    // ……以下 renderStackedHBar 的呼叫方式與現行完全相同，只是資料來源換成上面三個 map

    /* ---- 玩家排名兩張圖 ---- */
    const pgLabels   = playerRank.map(p => p.nickname);
    const pgWinData  = playerRank.map(p => Number(p.wins));
    const pgFailData = playerRank.map(p => Number(p.fails));
    renderStackedHBar('chartPlayerGamesRank', pgLabels, pgWinData, pgFailData, '#2980b9');

    const byScore = [...playerRank].sort((a, b) => Number(b.score_sum) - Number(a.score_sum));
    renderHBar('chartPlayerScoreRank',
        byScore.map(p => p.nickname),
        byScore.map(p => Number(p.score_sum)), '總積分', '#8e44ad');
}
```

`renderChart` / `renderStackedVBar` / `renderStackedHBar` / `renderHBar`
四個繪圖工具函式**完全不用動**，改的只是餵給它們的資料怎麼來。

### 2.3 已知取捨：跨日不重複人數

日彙總表能精確回答「某一天有幾人上線」，但無法回答「這 7 天總共有幾個不重複的人」——
這是所有 pre-aggregation 架構共同的限制（HyperLogLog 之類的近似結構在這個規模下不值得引入）。

三個選項：

| 方案 | 做法 | 代價 |
|---|---|---|
| **A（建議）** | 把卡片標題從「近 7 天上線人數」改成「單日最高在線」 | 零成本，語意清楚 |
| B | 仍走明細算精確值 | 只能算到保留期內；且保留期一縮短就失真 |
| C | 直接對 `player_daily_stats` 下 `count(distinct player_id)` 的 RPC | 精確，但要多一支 RPC；資料量小其實可行 |

C 其實比想像中便宜（`player_daily_stats` 一位玩家一天只有一列），
若你在意這個數字的精確性，我傾向直接做 C 而不是退讓成 A。

### 與草案不同的三個決定

1. **`playCount` → `clearCount` 的映射（草案漏掉的 bug）**
   子選單的 value 是 `playCount`，但 RPC 的 `p_mode` 只認得 `clearCount`。
   草案原文寫「sub 的三種值與 RPC 的 p_mode 同名」是**錯的**。
   實測直接傳 `playCount` 會落入 SQL 的 `else` 分支回傳 `best_score`——
   榜單標題寫著「累計通關」、數字卻是最高分，而且完全不會報錯。
   已在 `fetchGameBoard` 內加上一行映射，並在註解說明原因。

2. **「近 7 天不重複人數」採草案的 C 案（精確值），而非 A 案（改標題）**
   草案曾建議退讓成「單日最高在線」。實際查過資料量後改用 C 案：
   `player_daily_stats` 全表只有 157 列、近 7 天只有 7 列，
   直接把 7 天的列撈回前端去重完全沒有效能或截斷疑慮，
   沒有理由為此犧牲數字的正確性。

3. **頂部四張卡片改為「永遠代表今天／近 7 天」**
   舊版是從「已載入的明細」filter 出今天與近 7 天，所以只要使用者把
   日期範圍調到不含今天，四張卡片就會全部歸零——卡片標題寫著「今天」
   卻受下方圖表範圍影響，是舊版的邏輯瑕疵。新版獨立查詢，不受範圍影響。
   同時分日基準改為 Asia/Taipei（舊版用 UTC，台灣早上 8 點前會差一天）。

### 對帳結果

以「把 `game_logs` 明細分頁全撈回來逐筆重算」作為真值，與 RPC 回傳值比對：

| 對帳項目 | 結果 |
|---|---|
| `get_time_board` 前 5 名（玩家與秒數） | 一致 |
| `get_short_board(all)` 前 5 名（玩家與分數） | 一致 |
| `get_game_board` 高分／速通／累計通關（game1 小學） | 一致 |
| `get_daily_overview` 天數／過關數／失敗數／逐日人數 | 一致 |
| `get_game_diff_stats` 細格數／過關總數／失敗總數 | 一致 |
| `get_player_rank_stats` 前 5 名（玩家與局數） | 一致 |

⚠️ 對帳時如果分兩次取樣（先看畫面、再抓明細），數字會對不起來——
因為有玩家正在線上，`game_logs` 每分鐘都在增加（實測過程中從 5627 筆
長到 5642 筆）。必須在**同一瞬間**同時取 RPC 與明細才有意義，
這點在寫驗證腳本時很容易踩到。

⚠️ 速通榜與高分榜可能出現「多人同值」，此時 SQL 與其他語言對同值列的
排序本就不保證一致，對帳應比對「數值序列」與「同值者是否都在合法集合內」，
而不是硬比名次。

### 一併發現、但**未**處理的既有問題

- **難度榜（研究所征服榜／滿級分制霸榜）是空的。**
  這兩張榜讀 `player_saves.difficulty_counts`，但雲端所有玩家的這個欄位
  都是 `{}`。此路徑本次完全沒有改動，屬於改版前就存在的資料問題
  （`saveScore` 有寫入 `data.difficultyCounts`，但雲端沒有對應資料，
  推測是舊存檔累積下來的落差），需要另案追查。
- **`ranked_wins` 全部為 0。** 舊 LOG 沒有 `is_ranked`，backfill 一律歸為
  練習局（SQL 草案 §4.2 的預期行為）。SQL 執行之後的新局才會正確分流。
