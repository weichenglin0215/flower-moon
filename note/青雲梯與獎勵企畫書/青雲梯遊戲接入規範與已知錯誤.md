# 青雲梯 · 遊戲接入規範與已知錯誤

> 一款 `gameXX.js` 要能被青雲梯派出來當課程，需要滿足哪些**變數、函式與跨檔註冊**，
> 以及歷史上踩過的坑。
>
> **每次新增或修改遊戲後，務必執行：**
> ```
> node tools/verify_learning_path.js games    # 接入契約（本文件第二、三節）
> node tools/verify_learning_path.js poems    # 真的出得了題、出的是本站的詩、且具決定性
> ```
> 這兩節會把本文件的每一條規則對 `game1.js` ~ `game40.js` 各驗一次。
> 它不是靠正規表示式猜：
> - `games` 把遊戲模組載入 Node，**實際呼叫** `startNextLevel()` 看它有沒有做對事情。
> - `poems` **自動找出**每款遊戲真正的選詩函式（掃描哪一支的內文出現
>   `getSharedRandomPoem`），對 12,694 組「站 × 遊戲 × 必通關卡」各驅動兩次，
>   檢查出得了題、詩屬於本站、而且兩次結果一模一樣。
>
> 不維護「gameXX → 選詩函式名」對照表是刻意的：那張表就是第二份規格，
> 新增遊戲時一定會忘了加。
>
> 相關文件：
> - [青雲梯與文位晉升_總企畫書.md](青雲梯與文位晉升_總企畫書.md)（規格本體）
> - [文位升等已知錯誤紀錄.md](文位升等已知錯誤紀錄.md)（升等流程的坑）

## 〇、共同契約（2026-09-11 起）—— 39 款一律相同，沒有例外

> 作者指示：「即使是目前尚未納入『學習』或『考試』的遊戲也要先統一規範，
> 避免後續增加遊戲時造成困擾。」

**權威來源是 `gameContract.js` 的常數，不是這份文件。**
`FMGame.REQUIRED_METHODS` / `REQUIRED_FIELDS` / `FORBIDDEN_IN_GAMES`
由 `tools/verify_learning_path.js` 第 1 節直接拿去驗 39 款，
任何一款不符都是 ❌ —— **不再因為「這款還沒納入青雲梯」而降級為 ⚠**。

### 0.1 必備函式與變數

| 成員 | 簽章 | 語意 |
|---|---|---|
| `show()` | `()` | 開啟遊戲介面 |
| `stopGame()` | `()` | 關閉遊戲並**自行**隱藏 overlay |
| `startNewGame()` | `()` | 開新局（抽新題） |
| `retryGame()` | `()` | 重來（保留本題） |
| `startNextLevel()` | `()` | 關卡模式推進下一關　★青雲梯會暫時覆寫它 |
| `gameOver(win, reason)` | `(win, reason)` | 判定勝負，唯一的結算入口 |

變數：`isLevelMode`、`currentLevelIndex`、`difficultySettings`（五個難度層都要有），
**必須宣告在物件上**，不可以「等回呼裡第一次賦值才長出來」。

### 0.2 三件事一律呼叫共用函式

```javascript
startNextLevel: function () { window.FMGame.nextLevel(this); },       // 關卡推進
const onConfirm = () => { window.FMGame.advance(this, win); };        // 結算按鈕
window.FMGame.completeLevel('gameXX', this);                          // 通關紀錄
```

`FMGame.nextLevel` 是**全專案唯一允許 `currentLevelIndex++` 的地方**；
驗證工具現在的規則是「遊戲檔內一處都不准有」，不再是舊版的
「只能寫在 `startNextLevel` 裡」——因為舊規則擋不住「根本沒有 `startNextLevel`」
的情形（`game15`／`17`／`19` 就是這樣一路通過驗證的）。

### 0.3 ⛔ 遊戲內絕對不得出現

`MenuManager.closeAll()`、`closeAllActiveOverlays()`、`FMGoHome()`、
`MenuManager.goHome()`、`localStorage.*`

這些是全站層級的動作，青雲梯與考試無從得知：進行中的考試會被
`ExamEngine.forceStop()` 靜默殺掉（報名費白花）、課程局不會被記成失敗、
離場守門也不會解鎖。**要離開一律呼叫 `FMGame.exit()`** ——
它會先判斷現在有沒有課程／考試在進行，有的話交給青雲梯跳確認彈窗，
講清楚會損失什麼，玩家點頭才離開。

### 0.4 積分與文錢的讀取收口

`FMGame.getScore()`／`getSilver()`／`addSilver(amount, source, note)`／`getRankName()`。
文錢的**寫入**仍走 `FMCollectionSave.addSilver`（雲端流水帳的唯一收口），
這裡補的是讀取端。

### 0.5 隨手自我檢查

主控台輸入 `FMGame.audit()`，當場列出目前哪一款不合規。

## 一、三個等級：一款遊戲跟青雲梯的關係

| 等級 | 定義 | 判定依據 | 契約要求 |
|---|---|---|---|
| **課程遊戲**（★） | 青雲梯會派它出場，通關計入必通關卡 | 在 `learningPath.js` 的 `GAME_CHANNELS` 且不在 `REVIEW_ONLY_GAMES` | 本文件**全部**條款，缺一即為 bug |
| **複習池遊戲** | 只出現在複習池與漢堡選單自由練習 | 在 `REVIEW_ONLY_GAMES`（目前 21、23、36） | 只要第三節「共同必備項」 |
| **青雲梯外遊戲** | 完全不屬於青雲梯 | 其餘 | 只要第三節「共同必備項」 |

⚠️ **2026-09-11 修訂**：上表的分級只剩「選詩相關」的條款還適用（`getSharedRandomPoem`
與關卡種子）。**第〇節的共同契約對 39 款一律 ❌，不分等級。**
舊版對後兩類只給 ⚠（「現在沒事，但要納入課程之前必須先補齊」），
結果是 `game7`／`15`／`17`／`19`／`27`／`36` 六款長期帶著例外通過驗證 ——
而它們早就在漢堡選單的自由練習裡被玩了好幾個月。

> ⚠️ 一款遊戲能不能列入課程，硬性前提是它**必須透過 `getSharedRandomPoem` 取詩**。
> 自己實作選詩邏輯的遊戲無法保證「同一關＝同一首詩」，跨遊戲共用關卡表對它無效，
> 因此不能列入必通關卡（21、23、36 就是這樣被移出去的）。

## 二、★ 課程遊戲：青雲梯真正會呼叫到的東西

青雲梯派局的完整呼叫鏈（`learningPath.js` 的 `enterStation` → `launchGame` → `advanceAfterWin`）：

```
LearningPath.launchGame(gameNo, tier, levelIndex)
  ├─ LevelTable.setContext(tier, levelIndex)        指定難度層與關卡
  ├─ LevelTable.setAllowedPoemIds(本站的詩)          限制候選詩範圍
  ├─ 逐一 window['Game'+n].stopGame()               關掉其他還開著的青雲梯遊戲
  │      ↑ 迴圈跑的是 Object.keys(GAME_NAMES)
  ├─ 暫時覆寫 GameObj.startNextLevel = advanceAfterWin   ★收回關卡推進的控制權
  ├─ 暫時替換 DifficultySelector.show → callback(tier, levelIndex)
  └─ GameObj.show()
         └─ 遊戲呼叫 DifficultySelector.show(名稱, (難度, 關卡) => {…})
                └─ 拿到青雲梯指定的難度層與關卡 → startNewGame()
                       └─ getSharedRandomPoem(…, seed=currentLevelIndex, …)
                              └─ LevelTable.resolve() 查表拿到「這一關該出的那首詩」

玩家過關 → gameOver → GameMessage 的「下一關」
  └─ onConfirm → this.startNextLevel()   ← 已被覆寫，實際跑的是 advanceAfterWin
         └─ LearningPath 重新挑題、重新挑遊戲、判斷有沒有晉升
```

> ⚠️⚠️ `startNextLevel` 與 `DifficultySelector.show` **同時也是 `examEngine.js` 會暫時覆寫的函式**（考試逐題答題靠同一套機制接管遊戲）。兩個模組交錯時（例如考試進行中又被派了一局課程），若各自把「覆寫前看到的那一個」存起來，還原時會互相把對方的替身當成原版裝回去——這款遊戲從此永久停在別人的閉包上，且不會有任何錯誤訊息。修法是替身一律掛 `__fmOriginal` 指向真正的原版（`.agent/skills/花月開發常見錯誤與解法.md` §3.4），新增課程遊戲不需要為此多做任何事，但**若要另外對 `startNextLevel`／`gameOver`／`DifficultySelector.show` 動手（例如關卡挑戰模式），務必套用同一個模式**，否則會重新打開這個洞。詳見本文件 §4 №8。

### 2.1 必備函式

| 成員 | 型別 | 青雲梯在哪裡用 | 漏了會怎樣 |
|---|---|---|---|
| `window.GameXX` | object | 到處 | 完全叫不動這款遊戲 |
| `show()` | function | `launchGame` | 同上 |
| `stopGame()` | function | `launchGame` 換遊戲時、`menu.js` 全域清理 | overlay 疊在一起、或切頁後畫面被遮住 |
| `startNewGame()`（或 `startGameProcess()`） | function | `startNextLevel` 內部 | 過關後畫面停住 |
| `retryGame()` | function | 失敗重來 | 失敗後無法再玩 |
| **`startNextLevel()`** | function | **青雲梯暫時覆寫它** | **見 §4 №1 —— 最嚴重的一種** |

`startNextLevel()` 的標準寫法（唯一允許 `currentLevelIndex++` 的地方）：

```javascript
// ── 關卡模式過關後，關卡編號 +1 並開始下一關 ────────────
// ⚠️ 必須獨立成一支具名函式。青雲梯會在派局前暫時覆寫它，
//    好在每一關結束後把控制權收回去重新挑題、重新挑遊戲。
startNextLevel: function () {
    this.currentLevelIndex++;
    this.startNewGame();          // 若有 updateUIForMode() 就先呼叫它
},
```

驗證程式會**實際執行**這一支（把 `startNewGame` 換成偵測用的替身），確認：
1. `currentLevelIndex` 真的加了一
2. 真的呼叫了 `startNewGame()` / `startGameProcess()`
3. 這個屬性是**可寫的**（青雲梯的覆寫是「暫時替換再還原」，不可寫就會靜靜失效）

### 2.2 必備變數

| 成員 | 初始值 | 用途 | 漏了會怎樣 |
|---|---|---|---|
| `isLevelMode` | `false` | 是否為關卡模式 | 選詩退回隨機，青雲梯指定的詩不會出現 |
| `currentLevelIndex` | `1` | 目前關卡編號（＝`getSharedRandomPoem` 的種子） | 同上 |
| `difficultySettings` | 物件 | **五個難度層都要有**：小學／中學／高中／大學／研究所 | 青雲梯的站點會跨到缺的那一層，一進去就開不了局 |

> ⚠️ `difficultySettings` 內的 `minChars` 不得大於 `maxChars` ——
> 這種組合數學上無解，該難度層一進去就跳「載入詩詞失敗」，
> 而且錯誤訊息完全看不出原因。驗證程式會直接擋下來。
>
> ⚠️ 非經作者同意，禁止修改 `difficultySettings` 的內容（`.agent/skills/SKILL.md` 絕對禁止事項）。

### 2.3 必備行為（原始碼層級）

| 規則 | 正確寫法 | 為什麼 |
|---|---|---|
| 難度選擇器回呼收**兩個**參數 | `DifficultySelector.show('遊戲名', (selectedLevel, levelIndex) => {…})` | 青雲梯靠替換這支把難度層與關卡注入；只收一個參數時關卡編號會遺失 |
| 以 `levelIndex !== undefined` 判定關卡模式 | `this.isLevelMode = (levelIndex !== undefined);` | 全專案一致的寫法 |
| **`currentLevelIndex++` 只能出現在 `startNextLevel()` 裡** | 見 §2.1 | 寫在 `onConfirm` 等於繞過青雲梯的攔截點（§4 №1） |
| 過關結算走 `startNextLevel()` | `if (this.isLevelMode) this.startNextLevel(); else this.startNewGame();` | 同上 |
| 選詩傳入關卡種子 | `..., this.isLevelMode ? this.currentLevelIndex : null, 'gameXX')` | 沒種子就不會查關卡表，青雲梯指定的詩不會出現 |
| 過關要記錄 | `ScoreManager.completeLevel('gameXX', this.difficulty, this.currentLevelIndex)` | 青雲梯的進度**完全**由 `levelCleared` 推導，沒記錄等於這一局白打 |
| **查表條件不得隨機** | 關卡模式下所有影響 `getSharedRandomPoem` 參數的選擇（題型、句數、字數…）都要用 `currentLevelIndex` 推導，不可以 `Math.random()` | 見 §4 №6 —— 同一關每次拿到不同的詩，「同一關＝同一首詩」整組失效 |
| `stopGame()` 自己隱藏 overlay | `if (this.container) this.container.classList.add('hidden');` | `menu.js` 的全域清理只呼叫 `stopGame()`，不呼叫 `hide()` |

> `game40` 的種子寫法是合法的變體（`if (this.isLevelMode) hit = tryLens(this.currentLevelIndex); else …`），
> 驗證程式兩種都接受。

## 四、已知錯誤紀錄

### №1　`startNextLevel()` 缺席 —— 遊戲脫韁 · 2026-09 · game16「打地詩」🔴 最嚴重

**症狀**（玩家回報）
- 「童生二階」連續出現 **4 次 GAME16**，全部使用同一首詩 `poem_id = 375`〈山行〉。
- 關掉遊戲重開後換了別的遊戲，但**還是同一首詩**，前後共出現 8 次。

**根因**
`game16.js` 是 16 款課程遊戲中**唯一沒有 `startNextLevel()`** 的一款；
它把 `currentLevelIndex++; updateUIForMode(); startNewGame();` 直接寫死在
`gameOver` 的 `onConfirm` 裡。青雲梯只覆寫 `startNextLevel`，攔不到這條路徑，
於是 game16 一被派出就自己一路打下去，青雲梯完全失去控制權。

**為什麼會連同一首詩也重複**
青雲梯進站時會用 `LevelTable.setAllowedPoemIds()` 把候選詩鎖在本站的 2~6 首之內。
game16 自行遞增的關卡編號一旦超出本站安排的範圍，`LevelTable.resolve()` 的候選順序
是**完全決定性**的（錨定詩 → 同一首詩其他起始句 → 同題目群 → 同站其他詩），
於是每一關都解析到同一首詩的同一段：

```
level 173 → poem 375「山行」start=0 (anchor)
level 174 → poem 375「山行」start=0 (same-poem)
level 175 → poem 375「山行」start=0 (same-cluster)
level 176~181 → 全部 poem 375「山行」start=0
```

**連鎖災情**
1. 同一款遊戲連玩四五局不換（違反「同款最多連 3 局」）。
2. 每一關都是同一首詩的同一段。
3. `completeLevel` 把**別站**的關卡記成已通過，污染進度，進而引發 №2 的跨站跳躍。

**修正**：獨立出 `startNextLevel()`，`onConfirm` 改為呼叫它。

**驗證程式的三道防線**
- `startNextLevel() 存在` —— 物件層級
- `currentLevelIndex++ 只出現在 startNextLevel() 內` —— 原始碼指紋
- `劇本 A/B：同一款遊戲最長連續 N 局` —— 行為層級

### №2　`GAME_NAMES` 漏列 —— overlay 疊圖 · 2026-09 · game16

`learningPath.js` 的 `launchGame` 靠 `Object.keys(GAME_NAMES)` 逐一關掉
「還開著的其他青雲梯遊戲」。`GAME_NAMES` 漏列 game16，導致玩家沒通關就返回青雲梯、
再點另一個站時，game16 的 overlay 留在畫面上不會消失，新舊兩層疊著。

**教訓**：`GAME_NAMES` 不只是「顯示名稱」，它同時是一份**清理清單**。
只要是青雲梯可能派出的遊戲，都必須在裡面有名字。

### №3　`difficultySettings` 的 `minChars > maxChars` —— 該難度層永久卡死

`game37`「步步為陣」研究所難度曾設 `minChars: 40` 配 4 句，在現有詩庫中數學上無解，
玩家一進去就跳「載入詩詞失敗」然後停在那裡（已手動改成 28）。

現行的兩層防護：
1. `getSharedRandomPoem` 會把原因印到主控台（而不是只丟一句失敗）。
2. `launchGame` 會攔截該次失敗、**自動改派另一款遊戲**，玩家不會卡死。
3. 逃生口：同一關失敗 3 次後開放「捐納跳關」。

驗證程式的劇本 E 會刻意讓某一款遊戲完全出不了題，確認第 2 條安全網仍然有效。

### №6　查表條件被隨機化 —— 同一關每次拿到不同的詩 · 2026-09 · game20／game40

`getSharedRandomPoem` 是靠「難度層＋關卡編號＋這一局的題目需求」去查跨遊戲共用關卡表的。
**題目需求也是查詢條件的一部分。** 若遊戲在關卡模式下還把需求隨機化，
同一關每次問的就是不同的問題，關卡表回答的自然也是不同的詩：

| 遊戲 | 隨機了什麼 | 後果 | 受影響關卡 |
|---|---|---|---|
| `game20` 丟三落一 | `currentFormat` 從 `settings.formats` 隨機挑，而它決定 `needLines`（A=2／B=3／C=4 句） | 同一關拿到同一首詩的**不同聯**（實測 中學#24 → 304@0 與 304@2） | 4% |
| `game40` 點兵成詩 | 先試五言還是先試七言由 `Math.random()` 決定，兩者是兩個不同的 `minChars=maxChars` 查詢 | 同一關拿到**不同的詩**（實測 中學#128 → poem 12 與 poem 333） | 49% |

**為什麼嚴重**：必通關卡的定義是「同一組詩句用 3 款不同遊戲各通過一次」。
關卡指向的詩每次都在變，這條定義就失去意義 —— 玩家以為在複習同一聯，
實際上每次都在背新句子。

**修正**：關卡模式下改用 `currentLevelIndex` 推導，自由練習維持隨機。

```javascript
// game20
this.currentFormat = this.isLevelMode
    ? formats[this.currentLevelIndex % formats.length]
    : formats[Math.floor(Math.random() * formats.length)];

// game40
const lens = this.isLevelMode
    ? (this.currentLevelIndex % 2 === 0 ? [5, 7] : [7, 5])
    : (Math.random() < 0.5 ? [5, 7] : [7, 5]);
```

> 同一關永遠同一種寫法，不同關仍然輪替到所有題型／句式，不會偏食。

**自動驗證**：第 2 節「同一關同一遊戲永遠拿到同一首詩的同一段（決定性）」——
對 12,694 組（站 × 遊戲 × 必通關卡）各呼叫兩次比對。

### №7　`GAME_NAMES` 之外的清理清單：overlay 疊圖的第二種寫法

`launchGame` 在派新局之前會逐一關掉「還開著的其他青雲梯遊戲」，
迴圈跑的是 `Object.keys(GAME_NAMES)`，而條件是
`G.container && !G.container.classList.contains('hidden')`。

因此一款遊戲要能被正確清掉，需要**三件事同時成立**：
1. 在 `GAME_NAMES` 裡（§4 №2）
2. 有 `container` 屬性指向自己的 overlay
3. 有 `stopGame()` 且它會加上 `hidden`

三者缺一，玩家就會看到兩層遊戲疊在一起。

### №8　考試與青雲梯交錯覆寫同一支函式 —— 還原時把對方的替身當成原版 · 2026-09 修正 🔴🔴

**由「不變式 ＋ 亂序模擬」（第 11 節）自動找出來的，不是人想出來的；這是一整類錯誤，不是單一 bug。**

`learningPath.js` 覆寫 `GameXX.startNextLevel`／`DifficultySelector.show` 來接管關卡推進；
`examEngine.js` 覆寫 `GameXX.startNextLevel`／`GameXX.gameOver`／`DifficultySelector.show`
來接管答題流程。兩邊都是「存下我覆寫前看到的那一個，事後裝回去」的寫法。
**只要兩者交錯（考試進行中又被派了一局課程），還原就會把對方的替身當成原版裝回去**，
那支函式從此永久停在別人的閉包上——玩家自由練習過關會被導回別的模組的流程，
或是進自由練習時選不了難度，而且**完全不會有任何錯誤訊息**。

**修正（兩層）**
1. **擋掉交錯**：`onStationClick` 在 `ExamEngine.isBusy()` 時拒絕再開課程局。
2. **機制本身要安全**：三支函式、兩個模組全部改成 `__fmOriginal` 模式（見本文件
   §2 開頭的提示框，與 `.agent/skills/花月開發常見錯誤與解法.md` §3.4）。

**驗證**：`tools/verify_learning_path.js` 第 10.12 節對機制本身直接下測試——
兩種覆寫順序（青雲梯先／考試先）各驗一次還原後等於原版；第 11 節的亂序模擬
也把這條交錯納入不變式（「沒在考試、青雲梯也沒派局時，遊戲不得還被劫持」）。

### №9　六款遊戲各自為政 —— 「例外」本身就是 bug · 2026-09-11 全面統一 🔴🔴

**這一條不是某一個 bug，是一整類 bug 的根。**

玩家回報「考試中途某一題突然跳出難度選單，考試就沒了、報名費白花」之後，
作者的判斷是：問題不在 `game13` 那一行，而在於

於是把 39 款全部拉出來對照，結果如下 ——

### №10　青雲梯「零延遲同步呼叫」揭露動態 CSS 載入競態 · 2026-09 · game40「點兵成詩」

**症狀（玩家回報）**：game40 第一次被青雲梯派出時，答案棋盤的字塊字級變得非常小；
點「重來」後恢復正常。第一次修正用 `requestAnimationFrame` 等一幀再量測 DOM 尺寸，
仍然偶爾重現，第二次才找到真正病根。

**根因**：
`game16~40`（含 game24／game38／game40）的 CSS 都**不在** `index.html` 靜態
`<link>` 清單裡（`index.html` 只靜態引入到 `game15.css`），一律由各自
`loadCSS()` 在 `init()` 時動態插入 `<link>`，屬於非同步下載。
一般從漢堡選單進入時，玩家要在 `DifficultySelector` 對話框上**真人點擊**難度鈕，
這幾百毫秒的反應時間足夠讓 CSS 下載完成，所以「看起來沒事」。

但青雲梯 `launchGame()` 是在**同一輪事件循環內**直接呼叫 `GameXX.show()`——
`DifficultySelector.show` 被暫時替換成立即同步回呼（見本文件〇節／`learningPath.js`
的 `patchedShow`），沒有真人反應時間這個緩衝。若這是本頁面第一次開啟該遊戲，
它的 CSS `<link>` 常常還在下載中，此刻任何依賴該 CSS 才會生效的版面
（如 `display:grid`／`height:100%`）量出來的 `offsetWidth`／`offsetHeight` 是 0，
用它算出來的字級或尺寸就會被夾在下限或直接錯誤——**跟排版時機（是否等了一幀）
無關，跟這份 CSS 檔案是否已經下載完成有關**，多等幾幀只是恰好等到下載完成，
沒有真正解決問題（在較慢的網路或較忙的裝置上，重試次數不夠一樣會重現）。

**為什麼 GAME24／GAME38 沒發生**：兩者都不在 `learningPath.js` 的 `GAME_NAMES`
清單裡（不是青雲梯課程遊戲），從未被那條零延遲同步路徑呼叫過，只是**沒被觸發**，
不是寫法比較安全——`game24.js` 的 `renderBoard()` 一樣用
`boardEl.offsetWidth/offsetHeight` 量測，同樣的 CSS 動態載入方式，
若哪天被排進 `GAME_NAMES`，會出現一模一樣的 bug。
`game38.js` 則是架構上真正免疫：`_buildBoardDOM()` 用**固定邏輯像素常數**
（`BOARD_MAX_W`／`BOARD_AREA_H`，對應舞台固定 500×850）算 `tileSize`，
寬高與字級全部用行內樣式 (`el.style.width/height/fontSize`) 直接設定，
完全不必量測任何 DOM 元素，也就不必等任何一份 CSS 下載完成。

**修法（game40）**：字級改吃 `_resizeBoardWrapper()` 算好的格邊長
（`this._cellPx`），不再量測 `#game40-board` 本身。
`_resizeBoardWrapper()` 只依賴 `#game40-board-wrapper` 的 `offsetWidth`，
而它的 CSS（`.fmd-board-wrapper`）定義在 `theme_dark.css`——
`index.html` 一開始就靜態載入，不受本遊戲 CSS 下載進度影響，
從第一次呼叫就是穩定值，不需要 `requestAnimationFrame` 重試。

**通用教訓（往後新增／檢查 game16~40 任何一款）**：
> 若某個尺寸計算依賴「量測一個 class 定義在自己模組 CSS 裡的元素」，
> 而該模組 CSS 是動態載入（`game16~40` 全部如此），
> 這個測量在「零延遲同步呼叫」（青雲梯／考試引擎的 `_patchGame`）下就不安全。
> 兩種安全解法擇一：
> 1. 改量測「CSS 保證已經靜態載入」的祖先元素（如 `.fmd-board-wrapper`），
>    自己反推出需要的尺寸（本次 game40 的做法）。
> 2. 直接用固定邏輯像素常數，寬高字級一律行內樣式設定，
>    完全不依賴任何動態載入的 CSS（`game38` 的做法，架構上最乾淨）。
> 「等一幀（`requestAnimationFrame`）再量」**不是**安全解法，
> 只是把競態視窗縮小到看起來很難重現，不會真正消除。

**後續稽核（2026-09）**：把 `GAME_NAMES` 清單裡除了 game40 之外、CSS 也是動態
載入的 9 款（game16／20／21／22／23／31／33／36／37）逐一檢查同一類問題：

- 字級／格子尺寸計算：全部 9 款都**已經**是固定邏輯像素常數（如
  `game22`/`game23` 的 `CELL_PX`、`game37` 的 `GRID_WIDTH`、`game33` 的
  文字長度查表）或行內樣式，跟 game38 同一套安全寫法，**沒有中招**。
  game40 是唯一「介面沿用 GAME24 視覺語彙」時把 GAME24 那套量測寫法一併
  抄過來、又剛好被排進 `GAME_NAMES` 的一款，才獨獨它出事。
- 但有 7 款（game20／21／22／23／33／36／37）的**計時圓環**
  （`updateTimerRing`）共用同一種舊寫法：先無條件把量到的 `w`／`h`
  （可能是 0）設進 `<svg>` 的 `width`／`height`，量到 0 時只有內層
  `<rect>` 有擋（`if (rw<0||rh<0) return`，`game23`／`game37` 甚至連這層
  都沒有），外層 SVG 已經被設成 0×0。這一版是**自我修復**的
  （每 100ms~1000ms 的 tick 都會重算一次，下一次多半就量對了），
  不像 game40 的棋盤字級是一次性烘死，但仍是同一個根因在小範圍重現。
  `game31` 原本就已經有 `if (w === 0) return;` 這一道防線，不需要改。
  已比照補上同一道防線：量到 `w`／`h` 為 0 時整段跳過，不去動 SVG／rect
  的既有屬性，等下一次 tick 量到合理值再畫，避免計時外框在遊戲剛開始的
  一瞬間被畫成看不見的 0×0（僅此而已，量到正常值後行為與原本完全相同）。
