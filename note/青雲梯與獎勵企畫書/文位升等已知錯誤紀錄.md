# 青雲梯 · 文位升等已知錯誤紀錄

> 青雲梯的「站點推進 → 晉升彈窗 → 發放獎勵 → 考試冊封」這條鏈上，
> 歷史上踩過的每一個坑、成因、修法，以及**現在由哪一條自動驗證守住**。
>
> **每次改動 `learningPath.js` / `pathStations.js` / `exam*.js` 後，務必執行：**
> ```
> node tools/verify_learning_path.js flow
> ```
>

> - [青雲梯遊戲接入規範與已知錯誤.md](青雲梯遊戲接入規範與已知錯誤.md)（遊戲端的坑）

## 〇、先看懂這條鏈

```
玩家過關
  └─ ScoreManager.completeLevel()            寫入 levelCleared（唯一的進度來源）
       └─ 被覆寫的 startNextLevel → LearningPath.advanceAfterWin()
            ├─ invalidateProgress()          進度快取必須重算
            ├─ getCurrentStationIndex()      = PathStations.getCurrentIndex(getPathPoemCount())
            │      ↑ getPathPoemCount = 「依學習順序**連續**學會幾首詩」
            ├─ 站點索引前進了嗎？
            │     是 → showPromotionQueue(舊索引+1, 新索引)      ★逐站演出
            │            └─ showPromotionPopup(站, onNext)
            │                   ├─ grantStationReward()          ★彈窗出現「之前」就發獎
            │                   └─ 三種分支：小站／免考文位／需應試文位
            │     否 → 重新挑題、重新挑遊戲，繼續下一局
            └─（回到青雲梯畫面時）render() → settleArrivedRewards()   ★漏發的補刀
```

四個**必須同時成立**的性質：

| 性質 | 意思 |
|---|---|
| **逐站** | 一局可能跨過好幾站，每一站都要各自結算，不可以只處理最後一站 |
| **有序** | 彈窗依站點索引由小到大演出 |
| **冪等** | 同一站的獎勵只發一次（旗標 `achievements.claimed`） |
| **無漏** | 站點前進了就一定要發獎，不管玩家有沒有看到彈窗 |

## 一、已知錯誤

### №1　`getLearnedPoemCount()` 拿去定位站點 —— 整站被跳過 🔴

**症狀**：「考完塾生，塾生二階卻自己變成已完成」，中間好幾站一關都沒打過卻顯示已完成。

**根因**：站點定位靠 `PathStations.getCurrentIndex(n)`，它的判準是「`n >= 該站 poemFrom`
即已抵達」—— 這句話只有在**「這 n 首正好是學習順序的前 n 首」**時才成立。
但 `getLearnedPoemCount()` 數的是「總共學會幾首」，不管在哪學的；玩家在漢堡選單自由練習
打到後段的詩，總數就會灌水，站點跟著往前跳。

**修正**：另立 `getPathPoemCount()`，只數「依學習順序**從第一首起連續**學會的首數」，
並把站點定位收口成唯一一支 `getCurrentStationIndex()`。

> ⚠️ 全檔曾經有六處各寫一遍 `getCurrentIndex(getLearnedPoemCount())`，只要漏改一處就會再度跳站。
> **一律呼叫 `LearningPath.getCurrentStationIndex()`，不要自己組。**

**自動驗證**：第 3 節「`getCurrentIndex()` 在每一站的門檻上都指到正確的站」＋
劇本 A~B 的「站點索引單調不減」。

### №2　一局跨兩站時只演最後一站 —— 考試提示被吃掉 · 2026-09 🔴

**症狀**（玩家回報）：
> 「完成『童生』課程時，竟然沒有顯示要參加考試，也沒有參加考試就直接出現獎狀與獎勵動畫。」

**根因**：`advanceAfterWin()` 只彈 `stations[nowIdx]` **一個**彈窗。
但站點定位是「依序連續學會幾首詩」，只要中間某幾首詩早就被自由練習、溫習、
或別站派題時順手學完，補上缺口的那一局就會讓索引**一次前進兩站以上**。

實測重現（`node tools/verify_learning_path.js flow` 劇本 C）：

```
開局站 idx 11（準童生）→ 結束站 idx 13
【舊版實際彈出】 小站 → 童生二階          ← 獎狀＋獎勵動畫
【應該依序彈出】 ★應試資格 → 童生
                 小站 → 童生二階
```

童生站的「學問已成，可赴科場」引導彈窗被整個吃掉，演出的是童生二階的小站晉升動畫。
玩家看到的就是「沒叫我去考試，卻直接跳獎狀」。

**兩層災情**：
1. 中間若夾著需應試的文位站 → 考試引導消失（玩家找不到入口，雖然站點圖示上的
   「模擬考／正式考」標記仍在）。
2. 中間被跳過的小站／免考文位站 → 晉升文錢是在 `showPromotionPopup` 裡發的，
   沒彈窗就等於**永遠拿不到**。

**修正**：`advanceAfterWin` 改呼叫 `showPromotionQueue(fromIdx + 1, nowIdx)`，
逐站排隊演出；`showPromotionPopup(station, onNext)` 多收一個接續回呼串成佇列。

**自動驗證**：
- 劇本 C 專門製造跨站跳躍，斷言「跨過的每一站都依序演出」＋
  「中間的應試文位站演出的是『可赴科場』引導」。
- 劇本 A/B 的不變式：「每一局跨過的站都逐站演出晉升彈窗」（以佇列批次為單位比對）。
- 不變式「應試文位站一律走『可赴科場』引導，不發獎狀」＋「沒有播放晉升慶祝動畫」。

### №3　獎勵只在彈窗裡發 —— 四條路徑上的文錢永遠拿不到 🔴

**根因**：`grantStationReward()` 過去**只**被 `showPromotionPopup` 呼叫，
而那個彈窗只有「在青雲梯裡打完一局，而且按下『下一關』」這一條路徑會觸發。
實際上還有四條路會讓站點前進卻完全不經過它：

1. 過關後直接關掉遊戲、從漢堡選單走人
2. 捐納跳關（`donateSkip`）剛好補完這一站的最後一個單元
3. 在漢堡選單自由練習裡把某一站的關卡打完
4. 一局跨過好幾站，而玩家在中途的彈窗按了「即赴科場」

隨機壓力測試（25% 失敗、15% 過關後直接離開、10% 溫習）實測，一趟走到大儒
有 **9 站**的晉升文錢永久消失。

**修正**：新增 `settleArrivedRewards()`，在每次 `render()` 補發所有「已抵達但沒發過」
的站點獎勵。冪等旗標沿用 `achievements.claimed`。

> ⚠️ **效能陷阱**：`grantStationReward` 內部每呼叫一次就 `loadPlayerData()` 一次
> （＝`JSON.parse` 整份存檔）。無條件對近百個站點都呼叫，等於重繪一次青雲梯就解析近百次存檔
> —— 與 `buildProgressCache` 當初被加上快取的是同一個坑。
> 因此 `settleArrivedRewards()` **先讀一次 `claimed` 名單再過濾**，正常情況只會真的進去 0~2 站。

**自動驗證**：劇本 A~D 的不變式「已抵達的每一站都拿到了晉升文錢」＋
「金額正確、無重複發放」；劇本 D 專驗捐納路徑與冪等。

### №4　`rank_<文位>` 旗標被誤寫 —— 晉升文錢永遠領不到，且無錯誤訊息 🔴

**根因**：`grantPromotionSilver()` 用 `achievements.claimed` 裡的
`rank_<文位名>` 判斷「發過沒」。而成就殿堂舊版有兩處會提前寫入這個旗標：

1. 總覽頁的「領取稱號榜單」按鈕（積分升等時代的遺留）
2. 階級榜單以 `totalScore >= r.minScore` 判定「可領獎狀」，
   讓根本還沒考過的文位冒出「領取獎狀」按鈕

一旦被提前寫入，玩家將來真正晉升時，`grantPromotionSilver` 會認定「已經發過了」而回傳 0
—— **那筆文錢永遠領不到，而且沒有任何錯誤訊息**。

**修正**：
- 總覽頁一律直接顯示文位名稱，取消手動領取。
- 階級榜單改以 `getEffectiveRank()`（站點進度＋考試通過）判定，只提供「查看獎狀」。
- 「一鍵領取所有獎狀」明確擋掉 `rank_*` 開頭的 id。

> ⚠️ 沿用同一組 id 是**刻意**的：文位獎勵與成就頁的「領取獎狀」CTA 必須共用同一個冪等旗標，
> 否則玩家會在成就頁再領一次、造成重複發放。因此規則是
> **只有 `grantPromotionSilver` 與 `exam.js`／`examEngine.js` 可以寫 `rank_*`**。

**自動驗證**：第 5 節「重複發放被冪等擋下」＋「claimed 中 `rank_X` 只有一筆」。

### №5　越級考試補發時忘了 `includeExamRanks` —— 文位給了、獎勵沒給

`grantStationReward(station)` 預設會**跳過** `isExam` 的文位站，因為平常「抵達那一站」
只代表取得應試資格、還沒考過，本來就不該發獎。

但越級考試通過時已經把沿途文位**全部寫進 `ranks.passed`**（視同考過了），
這時再跳過就變成「文位給了、獎勵卻沒發，成就也沒標記」——
玩家的「領取獎狀」CTA 會一直掛在成就頁上，而且那筆文錢再也沒有機會補發。

**規則**：只有 `examEngine._grantSkipStations()` 該傳 `grantStationReward(st, true)`；
平常的「抵達站點」一律不要傳第二個參數。

**自動驗證**：第 5 節「沿途站點獎勵補發」「補發是冪等的」
＋「平常抵達應試文位站不發文錢」。

### №6　發獎勵與存檔的順序寫反 —— 剛發的文錢被舊資料覆蓋

`grantPromotionSilver` / `grantStationReward` 內部**各自**會 `load()` 一份存檔、
加完文錢再 `save()` 回去。因此 `examEngine._writeResult()` 必須
**先 `S.save(coll)`，之後才發獎勵**；順序寫反等於拿一份「發獎勵之前」的舊資料覆蓋回去。

實測災情：越級補發 34 首詩的沿途獎勵，結果文錢一毛都沒增加。

> 這與 `FMCollectionSave.addSilver` 當初刻意設計成「收 data、不自己存檔」是同一個坑。

### №7　群英榜自己抄一份文位判定 —— 榜上文位與自己看到的不一樣

群英榜的「文位榜」要替**別人**算文位，那些玩家的紀錄來自雲端 `player_saves`，
不在 localStorage 裡。若讓群英榜自己抄一套判定，「幾款遊戲算學會一關」
「哪幾款不列入進度」就會出現第二份定義，兩邊一飄移，玩家看到的自己的文位
與榜上的文位就會不一樣。

**規則**：判定邏輯抽成 `buildProgressMapsFrom(levelCleared, levelDonated)` /
`pathPoemCountFrom(maps)` / `isUnitDoneIn(maps, unit)`，本機與雲端共用同一份。
群英榜一律走 `LearningPath.getRankFromSave(row)`。

> ⚠️ **絕對不可以**改用 `row.global_rank`。那存的是**積分階級**
> （`getCurrentRank(totalScore)`），名稱與文位完全同名（書僮…大儒）卻是另一套判準，
> 直接拿來當文位顯示，等於在排行榜上公告「刷分就能升文位」——與企劃書 §2 相反。

### №8　`getStationRounds()` 的局數沒有夾上限 —— 通道權重整站失效

`getStationRounds()` 原本把一個單元的「已通關遊戲數」照實累加。
玩家在整站通關後仍可繼續複習（`pickUnit` 會改從全部單元隨機挑），
一個單元因此可能累積到四、五款遊戲的紀錄；`done` 於是超過 `total`，
`left = total − done` 變成負數，`pickGame` 的「站尾補缺」條件 `left <= 3` **永遠成立**
—— 整站從此不再依 12:3:3:1:1 權重挑通道，而是一直在補權重最低的通道。

**修正**：`done += Math.min(per, keys.length)`。

### №9　最後一站「大儒」點下去沒反應

大儒是整條青雲梯的最後一站，`poemFrom === poemTo`、`units` 為空。
`enterStation()` 過去在挑不到單元時只播一聲失敗音效就 return，玩家只會覺得點了沒反應。
現在會顯示「這一站沒有安排課程，青雲梯已至頂端。」

### №10　抵達應試站 ≠ 取得文位

企畫書 §4.1 的鐵則：

| 文位 | 取得方式 |
|---|---|
| 書僮／蒙童（免考） | 走到該站點的當下即完成晉升 |
| 塾生～大儒（應試） | 走到站點只代表**取得應試資格**；必須通過考試才算晉升 |

因此：
- 尚未應試時，`getEffectiveRank()` 一律封頂在**最後一個免考文位**。
- 站點圖示的「模擬考／正式考」標記條件是 `i <= currentIdx && 該文位還沒考過`，
  **不是** `i === currentIdx` —— 青雲梯的推進只看已學詩詞數，考試並不擋路，
  玩家很可能已經走過頭好幾站卻還沒回頭去考。用 `===` 會讓入口消失。

**自動驗證**：第 5 節「尚未應試時文位封頂在最後一個免考文位」。

### №11　彈窗站名兜錯 —— 「已通過『X』全部關卡，已具應試『X』之學力」

`_getPrevNextStationNames()` 要同時看兩件事才分得出「抵達」與「考試剛通過」：

1. `station.isExam` 是不是 true
2. `station` 是不是 `PathStations.build()` 陣列裡的**真身**

只看①會把「剛抵達的需應試文位站」誤判成通過考試；
只看②會把 Alt+W 測試熱鍵傳進來的合成物件也誤判成通過考試。
兩種誤判都曾做出同名兩次的句子。**兩者必須同時成立**才算「考試剛通過」。

### №12　應試資格早了一整站；考試不擋路 · 2026-09-05 定案並修正 🔴

**作者定案的三階段規則（以「狀元」為例）：**

| 階段 | 觸發 | 應發生 | 此時文位 |
|---|---|---|---|
| ① **入學** | 完成「準狀元」全部必通關卡 | 發晉升獎勵、站點推進到「狀元」、開始修狀元自己的課程。**尚無應試資格** | 榜眼 |
| ② **取得資格** | 完成「**狀元站自己**」全部必通關卡 | 應試入口開放（站點標記＋提示列＋一次性彈窗） | 榜眼 |
| ③ **冊封** | 通過狀元考試 | 發獎狀＋文位獎勵，關卡解除，得以續修「狀元二階」 | 狀元 |

**改版前的兩個錯**

**(a) 資格早了整整一站。** `getRankExamProgress()` 的分母用「文位里程碑首數」，
而那個數字**正好等於該文位站的 `poemFrom`** —— 也就是「剛踏進站、課程一關都還沒修」。
而考試範圍（`getScopeStations`）**本來就包含文位站自己的詩**，於是考卷上有一大塊
是還沒學過的：13 個文位中有 9 個「就算學過的每一題全對也到不了及格線」
（縣案首：及格 15/18，學過的最多只能對 12 題）。
改用該站的 `poemTo` 之後，13 個文位的考試範圍**全部**落在已學範圍內：

```
文位     入學(poemFrom)  修完(poemTo)  該站課程  考試範圍   修完後仍沒學過
塾生        16            18         2 首      8 首         0 首  ✓
狀元       263           271         8 首     57 首         0 首  ✓
大儒       346           346         0 首     75 首         0 首  ✓   （13 個文位全部 0 首）
```

> `getScopeStations()`（範圍含文位站本身）**本來就是照這套規則寫的**，
> 錯的自始至終只有資格判定那一支。

**(b) 考試完全不擋路。** 站點推進只看已學詩詞數，因此玩家可以一路走完全部 77 站
抵達大儒，**文位卻始終停在「蒙童」**（實測如此）。這讓文位不再代表進度，
「越級考試」這條路也失去存在的理由。

**修正**

- `getRankExamProgress(rankName)` 的分母改用該文位站的 `poemTo`。
- 新增 `getExamGateIndex()`：站點推進封頂在「第一個尚未通過考試的應試文位站」。
  `getCurrentStationIndex()` 改為 `Math.min(依詩詞數算出的站, 關卡站)`。
- 新增 `getExamGateState()`：回報「卡在哪一站／資格成立了沒」，供畫面共用。
- `showPromotionPopup` 的 `isExamRank` 分支從「學問已成，可赴科場」改成
  **「入室升堂」**（入學語氣、不導向考棚、不播慶祝動畫）。
- 新增 `showExamQualifiedPopup()`：修完文位站課程時才跳「可赴科場」。
- `render()` 的站點應試標記從 `i <= currentIdx` 改為以 `getExamGateState()` 為準。
- `renderNotice()` 在卡關時提供常駐的「前往應試」入口；進度條改顯示
  「『狀元』課程已修畢 —— 中式方可續進」。
- `startExam()` 自己也擋一道資格檢查（畫面是「顯示與否」，這裡是「能不能真的開考」）。

> ⚠️ **不會造成死鎖**：正式考沒有次數限制（只收文錢），文錢可以靠漢堡選單的
> 自由練習賺；卡在關卡站時該站的必通關卡還能反覆重打（`pickUnit` 在整站通關後
> 會改為隨機重抽）；模擬考每日免費一次；真的想跳過還有越級考試。

### №14　關卡編號會隨題庫擴充整批位移 · 2026-09-06 修正 🔴🔴 最高風險

**題庫一擴充，全服玩家的通關紀錄就會指向錯的詩，而且完全不會報錯。**

**成因**

`levelCleared` 的結構是 `{ 遊戲: { 難度層: [關卡編號…] } }`，
而「關卡編號」就是 `LEVEL_TABLE.tiers[層].levels[]` 的**陣列位置**。
那個陣列由 `tools/build_level_table.js` 依
「評價由低到高 → 詩句總評價由高到低 → id 遞增」重新排出來 ——
**只要新增詩詞，編號就會整批位移**。

實測（新增評價 7×5、6×8、5×10、4×18 共 41 首）：

| 難度層 | 舊關卡數 | 新關卡數 | 第一個指向不同詩的關卡 | 受影響 |
|---|---|---|---|---|
| 小學 | 25 | 35 | — | 0% |
| 中學 | 352 | 378 | #252 | 27% |
| **高中** | 660 | 716 | **#5** | **98%** |
| **大學** | 686 | 798 | **#40** | **87%** |
| 研究所 | 795 | 867 | #696 | 12% |

高中 98%、大學 87% 是因為排序主鍵是「評價由低到高」，
新增的評價 5／4 的詩會排到那兩層的**最前面**，把整層往後推。

**災情**：玩家的 `levelCleared['game4']['高中'] = [5, 12, 33…]` 這些數字
**還在、但指向完全不同的詩**。進度不會報錯，只會靜靜地全錯 ——
成就統計、已學詩詞數、青雲梯站點進度一起歪掉。

**修正：改用「內容識別碼」**

```
"<錨定詩 id>:<起始句索引>"      例如 "69:4" ＝〈將進酒〉第 5 句起的那一聯
```

它描述的是內容本身，關卡表怎麼重排都指向同一組詩句。

| 檔案 | 改了什麼 |
|---|---|
| `levelTable.js` | 新增 `getLevelKey` / `getLevelIndexByKey` / `toLevelKey` / `isLevelKey` |
| `scoreManager.js` | `completeLevel` / `markLevelDonated` / `isLevelDonated` / `recordLevelFail` / `getLevelFails` 一律走識別碼；新增 `_migrateLevelKeys()` 一次性遷移舊存檔 |
| `learningPath.js` | `buildProgressMapsFrom` 讀取時正規化（新舊格式都吃）；新增 `_unitKey()` 供站點的必通關卡比對 |
| `level-selector.js` | 星星顯示改以識別碼比對 |

**實測效果**（抽樣 100 關，模擬新增 41 首詩）：

```
存「關卡編號」→ 45 關指向不同的詩（45%）
存「識別碼」  → 0 關指向不同的詩（0%）
```

**三個必須記住的規則**

1. ⚠️⚠️ **遷移必須趕在下一次擴充題庫之前上線。**
   換算是拿「目前的關卡表」把編號翻回詩句，只有在關卡表還沒被新詩打亂之前才正確。
   等題庫改了才遷移，翻出來的會是錯的詩。
2. ⚠️ **關卡表未載入時不可以標記為已遷移。**
   `_migrateLevelKeys` 查不到表就直接跳過（不寫版本旗標），下次載入再試。
3. ⚠️ **讀取端必須同時吃得下新舊兩種格式。**
   群英榜讀的是**別人**的雲端存檔，那些玩家可能還沒開過新版。
   `buildProgressMapsFrom` 因此一律先正規化再建表。

**刻意沒改的**：`levelProgress[遊戲][難度層]`（該層最高通關關卡）維持關卡編號。
它的語意就是「排到第幾個」，只供選關畫面的解鎖判斷，不參與任何進度計算；
題庫擴充後會失準，但那只是選關畫面多開／少開幾格，
不會像 `levelCleared` 那樣讓進度指向錯的詩。

**自動驗證**：`node tools/verify_learning_path.js keys`
—— 第 9 節會真的用 `build_level_table.js` 產生一份「加了 41 首詩」的關卡表，

### №15　開機瞬間開青雲梯，道路停在「大儒」而不是「書僮」· 2026-09-06 修正

**新玩家第一次看到的畫面，捲動位置是隨機的。**

**成因**

`menu.js` 的 `showHomeOnBoot()` 在 `DOMContentLoaded` 那一刻就直接呼叫
`LearningPath.show()`——這是整頁最早、版面最不穩定的時間點：

- `learningPath.css` 不是寫在 `index.html` 的 `<head>` 裡，而是
  `LearningPath.init()` 執行到的當下才動態插入 `<link>`（見「花月開發常見
  錯誤與解法」§3.3 的 loadCSS 防護模式）。插入的瞬間瀏覽器連抓都還沒抓，
  `#lpScroll` 這時候連 `overflow-y:auto` 都還沒生效——**此時就算把
  `scrollTop` 設成算好的目標值，也會被瀏覽器直接夾回 0**（還不能捲的
  容器，捲動位置永遠是 0）。
- 原本只靠一次 `setTimeout(50)`（後來一度改成「立刻捲一次＋rAF 補一次」）
  賭版面會在時限內穩定，賭輸的話**沒有任何東西會再補捲第二次**，
  於是就這樣定住：`scrollTop = 0` 對應到道路最上方（索引最大、也就是
  文位最高的「大儒」，見 `scrollToCurrent()` 的座標換算），畫面因此停在
  大儒，而不是新玩家真正該在的「書僮」。
- 實測發現這個 race 並非每次都會發生（本地測試中偶爾第一次就穩，偶爾
  要到第二輪 reflow 才穩），純看 CSS 檔案實際讀取花了幾輪畫面更新，
  故意重現時要連續清空 `localStorage` 重整好幾次才會撞到。

**修正**：`LearningPath.show()`（`learningPath.js`）改成連續補捲好幾輪——
立刻捲一次＋三次 `requestAnimationFrame` 疊加補捲＋一個 `300ms` 的保底
`setTimeout`，涵蓋「版面要兩三輪 reflow 才穩定」到「CSS 真的要走一趟
網路請求才回來」的各種情形。不能只用 `setTimeout` 取代 `rAF`：分頁在
背景時 `rAF` 會被瀏覽器暫停，但這裡是剛開面板，理應在前景，兩者搭配
才兼顧「盡快捲到位」與「萬一真的卡很久也要有保底」。

**順便加的長期功能**：`render()` 现在只要站點是「目前所在站」且不是
「可應試」狀態，就會在圖示正下方疊一個持續縮放的 👆 手指提示
（`.lp-finger-hint`，`pointer-events:none` 不擋點擊），每次開啟青雲梯、
每次重繪都會跟著「目前所在站」一起出現，提醒玩家該點哪裡。可應試的站
不疊加，因為那裡已經有 `.lp-exam-real` 自己的脈動徽章在催促玩家去考試，
兩個一起跳反而互相搶焦點。

**蒙童是全部 15 個文位裡唯一設計成不用考試的一個，卻被自動排點的小考波及。**

**成因**

檔案最上方 `EXAM_FROM_RANK = '塾生'` 講得很清楚：「只有蒙童維持免考」。
但小考（`_markExams`）是後來才加上去的機制，做法是把「書僮 → 第一個
應試文位」這一整段也當成普通區間，按每 12 首一場的頻率均分切考——

於是切出一場小考塞在「準蒙童」，變相讓蒙童也要考試，
直接牴觸「蒙童免考」的既定設計。

**修正**：`pathStations.js` 的 `_markExams` 對**第一個錨點**（也就是
「書僮 → 塾生」這一段）強制 `need = 1`——不管這段實際有幾首詩，
一律不插小考，只留錨點本身（塾生）那一場文位考。其餘錨點之間的
區間（塾生→童生、童生→縣案首……）不受影響，仍照每 12 首一場的頻率
正常排點。

**驗證**：`node -e` 直接檢查站點結構，確認「準蒙童」「蒙童」的
`examKind` 都是 `null`，第一場考試（`examKind:'rank'`）落在「塾生」；
`node tools/verify_learning_path.js` 全數通過（考試總數由 33 場降為
32 場，小考由 20 場降為 19 場，其餘不變）。

### 劇本 F 的終局檢查（旗艦劇本）

一位玩家從全新存檔開始，走完 77 站、2,517 局、13 場考試之後：

預設每個文位**先落榜 3 次再通過**（共 52 場考試，可用 `FM_EXAM_ATTEMPTS` 調整）。

| 檢查 | 期望 |
|---|---|
| 站點 | 走到最後一站「大儒」 |
| 考試 | 13 個應試文位各考 4 次、只通過 1 次；落榜 39 場一律不冊封、不發獎勵 |
| 覆蓋率 | 15 個文位站與 62 個小站**全部走過** |
| 獎狀 | 免考文位抵達時 2 張、應試文位通過時 13 張；落榜 0 張 |
| 文位順序 | 塾生 → 童生 → … → 狀元 → 大儒，不跳級也不倒退 |
| 詩詞 | `getPathPoemCount()` 與 `getLearnedPoemCount()` 都等於題庫總數 346 |
| 獎勵 | 全部 77 站的 `claimed` 旗標齊全，且沒有任何一筆重複 |
| 局數 | `pathRounds` 等於實際勝場數 |
| 遊戲 | 16 款課程遊戲**每一款都真的被派出過**（設定表沒有死角） |
| 加上 | I0~I11 全部不變式 |

> ⚠️ 劇本 F 曾經抓到一個容易被忽略的邊界：**最後一站「大儒」自己沒有課程**
> （`poemFrom === poemTo`、`units` 為空），玩家抵達之後唯一還能做的事就是應考。
> 驗證程式的迴圈若寫成「走到最後一站就收工」，大儒的考試永遠不會發生，
> 整條青雲梯會停在狀元 —— 考試的判斷必須放在「收工」之前。

### 考試流程的檢查（第 6 節）

| 檢查 | 為什麼 |
|---|---|
| 沙箱期間 `completeLevel` / `saveScore` 被中和 | 企畫書 §6.5：考試是驗收不是練習 |
| 整場考試沒有增加 `pathRounds`、沒有推進站點、沒寫 `levelCleared` | 同上 |
| 拆箱後 `completeLevel` / `saveScore` / `alert` / `LevelTable` 情境全部還原 | 沒還原＝自由練習從此壞掉且無錯誤訊息 |
| 落榜：不冊封、不發獎、報名費不退、記入 `failCount` | №4 |
| 模擬考：不冊封、不發獎、不收費、一天一次 | 模擬考成績列入正式紀錄＝考試制度失效 |
| 越級：沿途文位一併冊封、站點視同完成、獎勵補發、**不偽造 `levelCleared`** | №5 |
| 報名費金額（走 `addSilver` 的 `exam_fee` 流水帳判定） | 見下方註記 |

> ⚠️ 報名費**不可以**用「餘額前後差」來驗。考試結束時 `onDone` 會呼叫
> `LearningPath.show()` → `render()` → `settleArrivedRewards()`，
> 把先前累積未發的晉升文錢一併補上，餘額差因此混了兩筆完全不同的帳
> （實測：落榜明明扣了 75，餘額卻反而多了 45）。
> 一律改看 `FMCollectionSave.addSilver` 的流水帳，依 `source` 分開記。

### 狀態潔淨度（第 7 節）

青雲梯派局與考試沙箱都會「暫時覆寫全域函式再還原」，漏還原是**靜默災難**：
玩家從漢堡選單進自由練習時會出現無法解釋的行為，而且不會有任何錯誤訊息。
因此在所有劇本跑完之後，逐一比對開場快照：

- 16 款課程遊戲的 `startNextLevel`
- `DifficultySelector.show`、`window.alert`
- `ScoreManager.saveScore`、`ScoreManager.completeLevel`
- `LearningPath.stopGame()` 之後 `LevelTable` 的候選詩白名單必須是 `null`
- 溫習模式不增加累計局數，但仍照記通關紀錄
- 捐納跳關：失敗未達門檻不開放、達門檻後開放、捐納後視同通過
- 走過頭之後，應試站仍然標示為「可應試」（`i <= currentIdx`，不是 `===`）

## 四、目前的驗證規模

```
node tools/verify_learning_path.js          # 全部，約 1,500 項檢查
node tools/verify_learning_path.js games    # 第 1 節　遊戲接入契約
node tools/verify_learning_path.js poems    # 第 2 節　真實出題（12,694 組）
node tools/verify_learning_path.js path     # 第 3~4 節 設定表與站點結構
node tools/verify_learning_path.js flow     # 第 5 節　升等流程（劇本 A~F）
node tools/verify_learning_path.js exam     # 第 6 節　考試與越級考試
node tools/verify_learning_path.js hygiene  # 第 7 節　狀態潔淨度
node tools/verify_learning_path.js money    # 第 8 節　文錢收支（應試負擔）
node tools/verify_learning_path.js keys     # 第 9 節　關卡編號穩定性
node tools/verify_learning_path.js report   # 跑一趟完整生涯，輸出玩家歷程 LOG
node tools/verify_learning_path.js -v       # 連通過的項目也列出

FM_EXAM_ATTEMPTS=1 node tools/verify_learning_path.js flow   # 劇本 F 每個文位只考一次
```

環境由 `tools/fm_env.js` 提供：它只補一個最小的瀏覽器環境
（window／document／localStorage／AudioContext…），
然後把 13 個核心模組與 39 款遊戲**原封不動**載入 Node。
驗證程式裡沒有任何一行是「另一份文位升等規則」。
